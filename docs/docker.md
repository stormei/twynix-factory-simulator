# Docker deployment

The image serves the Angular frontend, backend API, WebSocket updates, SQLite library and encrypted OPC UA server together. One container provides **one live runtime**; multiple saved projects and isolated agent previews are supported. Concurrent live simulations need separate containers, ports and volumes. No external database is required.

## First deployment

Install Docker Engine with the Compose v2 plugin on Linux, or Docker Desktop. Node.js 22.22.3+ is needed only to run the credential helper; the image build supplies its own Node.js and compilation tools.

```sh
git clone https://github.com/stormei/twynix-factory-simulator.git
cd twynix-factory-simulator
npm run docker:setup -- --host 192.168.1.149
docker compose --env-file .env.docker up --build -d --wait
```

Replace the example IP with the **Docker host's address reachable by OPC UA clients**, not the container's private address. The helper creates `.env.docker` with unique operator and API credentials, restricted file permissions, and loopback-only web access. It never overwrites an existing file. No package installation is needed to run the helper. `.env.docker` is excluded from Git and the Docker build context; keep a protected backup.

If Node.js is not installed on the host, use Docker to run the same helper instead of `npm run docker:setup` (Linux/macOS):

```sh
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/work" -w /work \
  node:22.22.3-bookworm-slim node scripts/docker-setup.mjs --host 192.168.1.149
```

Open `http://localhost:3000` on the host. In the application, select **Access token** and enter the `API_TOKEN` from `.env.docker`. The API and WebSocket connection require it; the static login page remains accessible without a token.

For LAN web access, set `WEB_BIND_ADDRESS` in `.env.docker` to the host's LAN IP and recreate the service. Use a TLS reverse proxy for remote access, forwarding WebSockets and the original Host header. A server reached over HTTP exposes the API token to that network, so use HTTPS for shared or untrusted networks.

```sh
docker compose --env-file .env.docker up -d --wait
docker compose --env-file .env.docker ps
docker compose --env-file .env.docker logs -f --tail 100
```

The image runs as the unprivileged `node` user. Compose drops Linux capabilities and enables no-new-privileges. It uses a named volume; new volumes get the image's data-directory ownership. If replacing it with a host bind mount, provide write access for UID/GID 1000 first. Do not run as root to work around ownership.

## Configuration

| Variable | Meaning / default |
| --- | --- |
| `API_TOKEN` | Required browser/API bearer token; generated by helper |
| `OPCUA_PASSWORD` | Required operator password, at least 12 characters; generated by helper |
| `OPCUA_USER` | Operator username, default `operator` |
| `OPCUA_HOST` | Required advertised address reachable from clients; choose before first startup |
| `OPCUA_PORT` | OPC UA listener and published port, default `4840` |
| `OPCUA_BIND_ADDRESS` | Host binding for OPC UA, default `0.0.0.0`; narrow to the LAN IP if desired |
| `WEB_BIND_ADDRESS` | Host web binding, default `127.0.0.1` |
| `WEB_PORT` | Host web port, default `3000` |

Compose fixes the internal API port to 3000, data directory to `/app/data`, and disables the unsecured OPC UA development profile. Environment changes require `up -d` to recreate the service; `restart` alone does not apply them. Firewall rules should restrict OPC UA to intended clients. Optional place search and forecast download require outbound HTTPS; saved weather and manual weather run offline.

Health checks authenticate internally and confirm both API and OPC UA readiness. `unhealthy` diagnoses failure but Docker's restart policy only restarts a process that exits. Investigate logs rather than assuming an unhealthy container is automatically restarted.

## OPC UA and ThingsBoard

Connect to `opc.tcp://YOUR_DOCKER_HOST:4840` using Basic256Sha256 / SignAndEncrypt and the configured operator credentials. Exchange and verify application certificates on both sides. Client trust and the server identity persist in `simulator-data` under `pki`.

```sh
# Inspect certificates rejected during a connection attempt.
docker compose --env-file .env.docker exec simulator sh -c 'ls /app/data/pki/rejected'
# Export the public server certificate for your client.
docker compose --env-file .env.docker cp simulator:/app/data/pki/own/certs/certificate.pem ./server-certificate.pem
```

After verifying a rejected client's certificate fingerprint, move only that certificate into `/app/data/pki/trusted/certs` inside the container and reconnect. Do not enable automatic trust. See [OPC UA tags and ThingsBoard's Base64 keystore requirement](solar-opcua.md#thingsboard-integration).

A new volume creates a new server identity. Existing locally generated client trust is not automatically copied into Docker. Changing `OPCUA_HOST` after certificate creation may require deliberate certificate renewal and client trust updates; retaining the volume preserves the old certificate rather than silently rotating it.

## Persistence, backups and upgrades

Save project edits explicitly. SQLite projects, reports and PKI are stored in the named `simulator-data` volume. Restart restores the last saved project in a **stopped initial state**. Runtime process values and active sessions are not resumed.

For a consistent backup, stop the service, copy the entire directory, then start it again:

```sh
docker compose --env-file .env.docker stop
mkdir -p backup
docker compose --env-file .env.docker cp simulator:/app/data/. ./backup/
docker compose --env-file .env.docker start
```

Backups contain private keys and should be kept encrypted with restricted access. Back up `.env.docker` separately. To restore, stop the target container, copy the backup contents into its `/app/data` volume, ensure UID/GID 1000 can write them, and start it. Preserve the original backup before attempting upgrades or restores.

```sh
git pull --ff-only
docker compose --env-file .env.docker up --build -d --wait
```

Use a release tag or recorded Git commit for repeatable builds. `docker compose down` retains data; **`down -v` deletes the volume**. Do not use `-v` for routine upgrades. The existing simulator on ports 3000/4840 must be stopped or use different deployment ports before starting this container.

## MCP

The image also includes the stdio MCP adapter. It is not an HTTP endpoint or another published port. An MCP host on the Docker machine can launch it through `docker compose --env-file /absolute/path/to/.env.docker -f /absolute/path/to/compose.yaml exec -T simulator node --import tsx apps/mcp/src/main.ts`. Set `TWYNIX_BACKEND_URL=http://127.0.0.1:3000` with `exec -e` if needed; the container's API token is already inherited. Do not allocate a TTY for MCP. See [MCP tools and access controls](mcp.md).

## Validation status

The Docker workflow builds the image, starts the secure deployment, checks health and frontend delivery, rejects unauthenticated API access, and verifies certificate identity survives container recreation. Native application build, unit/integration and Playwright tests run first. The workflow currently exercises Linux amd64; other architectures and target-host deployments need validation on their actual hosts. No prebuilt registry image is published by this workflow.
