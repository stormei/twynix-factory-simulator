# Architecture and implementation status

## Ownership and packages

`apps/web` is a standalone, signal-driven Angular application using Angular Material buttons/tooltips, SVG symbols, native pointer events, SCSS tokens, and a same-origin API. Selection, viewport, clipboard, and edit history are local UI state. It never computes process physics.

`apps/server` owns one active project/runtime, Fastify HTTP/WebSocket endpoints, a SQLite project library, startup/shutdown, and structured Pino logs. Multiple browser clients observe the same runtime. Editing requires pause/stop and restores initial conditions. Concurrent editing is currently last-write-wins; this is a single-engineering-workspace release, not a collaborative editor.

Packages separate versioned types/validation, equipment metadata and actuator models, process-graph validation/traversal, control ownership/hysteresis, scheduled fault scenarios, deterministic simulation, and OPC UA publication. The shared model contract is exported. SVG symbols are separate from the equipment physics.

## Determinism and overload

Physics uses fixed 100 ms steps. A monotonic wall clock accumulates elapsed time multiplied by speed. At most 50 steps execute per scheduler dispatch. A backlog above 5 simulated seconds pauses execution with an explicit diagnostic; no steps are silently dropped. Resume starts a fresh wall-clock accumulation from the current process state. Pause/stop retain physical state; Reset restores the initial project definition, seed, volume, commands, and faults. Simulation time uses integer deciseconds to avoid accumulated clock drift.

Execution is sorted by stable equipment ID. Controllers read the previous completed state, then actuators advance, fluid paths resolve, and process/sensor states advance. A seeded LCG drives measurement noise. Identical configuration, seed, command/fault step schedule produces identical outputs. Wall-clock/source timestamps are metadata and intentionally not deterministic physics inputs.

## Fluid assumptions

This is a bounded serial-path, incompressible water model, not a hydraulic network solver. Each fluid port accepts at most one connection; tees/manifolds are not supported. Source flow is limited by pump nominal flow × actual speed and the product of valve openings/coefficients. Pipes apply configurable conductance. Tank outlets use a simplified gravity relation, 20 L/s × sqrt(level fraction). Open terminal paths discharge to an implicit drain; disconnected devices have zero process flow.

Tank mass balance uses liters and L/s, with available source volume and destination capacity limiting flow before integration. A visited-ID path walk prevents recursion in cycles. Tanks form storage boundaries, so connected recirculating paths use previous-step storage constraints. Cycles without storage cannot spontaneously create fluid. Empty/full boundaries are conservative (a full tank may resume inlet flow one step after drainage creates space).

Pump speed ramps over configured rampTime. RunFeedback is based on actual speed, not the command. Current/power are simplified speed-dependent approximations, not a motor/pump curve solver. Trips/overheating remove pump output immediately. Fail-to-start blocks acceleration. Valve motion, actuation delay, leakage and stuck faults affect flow. Sensor filtering, seeded noise, offset, drift, bounded delay (maximum 60 s), stuck and invalid quality affect measured values, not process volume.

Pressure is a flow-related approximation. Photoelectric sensors can observe a connected conveyor's detection value. Electrical network solving is not implemented.

## Connected production model

The Packaging Line example is a serial material network: feeder → conveyor → finite buffer → machine → inspection → finished goods. Each product has a stable runtime identity, creation time, travel/process progress and rejection flag. Product ownership lives exclusively in `MaterialRuntime`, independently of SVG rendering. The invariant is **generated = good output + rejected output + work in progress**. No disconnected machine creates products. Material connections remain one-to-one; merges/splits, batches, product recipes and routing policies are future work.

The feeder emits a product at its configured interval while enabled and holds at most one waiting product. A conveyor has a capacity of max(1, floor(length in metres)), capped at 100 products, with one-metre pitch; speed and actual drive speed determine travel time. Spacing prevents packages overlapping behind a blocked head product. Buffer capacity is an integer from 1 to 100. Machines and inspection stations hold one product each; cycle progress depends on actual speed. Inspection applies a seeded Bernoulli reject rate at cycle completion. Rejected products continue to the final collector and are counted separately from good output. The final collector (or a terminal product counter) consumes products; unconnected outputs are blocked, not implicit drains.

Transfers are staged from the completed step and use pre-transfer destination capacity. Each product traverses at most one connection per 100 ms step, including buffer handoff, and no recursive propagation occurs. A destination that becomes free this step is available on the next step. Blockage propagates through finite queues; lack of material starves downstream stations. Jams/trips freeze material processing immediately, even while a drive's commanded stop ramps down. Drive RunFeedback means physical drive motion; station status separately distinguishes productive running, starvation, blockage, stopped, jammed and faulted. Power has a simplified idle-load allowance at starved/blocked processing stations.

Live metrics include good/rejected output, WIP, good-output throughput (pcs/hour over elapsed simulated time including startup), average completed-product lead time (includes queues and rejected completions), and mean busy utilization across machines/inspection stations. Station statistics count busy, starved, blocked, fault/jam and stopped seconds. Buffer waiting is not machine utilization. The fault-time total sums equipment fault seconds; overlapping faults are counted per equipment, not as unique line downtime. The “busiest workstation” indicator ranks processing-station utilization; it is a constraint clue, not a formal bottleneck proof or OEE calculation. Counts/queues and aggregate production metrics are readable through OPC UA.

## Scenarios and experiments

The Experiments workspace authors activation/clear fault windows through the existing validated project schema. These are saved with the project and replayed after Reset. Editing a schedule follows the same pause-and-restore policy as other configuration edits. Imported schedules may also contain any supported fault.

The comparison UI runs Baseline, Larger Buffer and Faster Machine variants against the same initial configuration, deterministic seed, duration and fault schedule. The engine uses isolated Simulation instances and yields every 100 process steps so the authoritative live runtime and OPC UA continue running. Durations are 10–1800 simulated seconds; at most four variants, one concurrent comparison request, and two million equipment-steps per report are allowed. Invalid overrides are rejected before running any variant. Report IDs/timestamps are metadata; result metrics replay deterministically.

SQLite stores the complete starting project definition, seed, duration, overrides and result metrics for each report. The UI lists the ten newest reports for the active project, including unsaved project definitions with that same ID. Comparisons include startup effects and are single-seed experiments, not statistically validated estimates or automatic optimization. Changing buffer space need not improve a line limited by processing capacity. Experiments always start from initial conditions rather than cloning the live physical WIP.

## Control and faults

Manual commands originate in the app; external commands originate in OPC UA; automatic pumps belong to enabled level controllers. Low/high hysteresis prevents cycling. Trip/overheat reject starts. Commands are accepted synchronously and motion completes on later physics steps. The JSON schema contains declarative controllers and timed fault scenarios; no arbitrary JavaScript executes. Scenario rules are applied at step boundaries. Manual fault activation and clearing is recorded in the bounded runtime event log. Faults not applicable to an equipment type have no physical effect in this release.

## Persistence and lifecycle

SQLite uses WAL and stores versioned project JSON plus metadata. Runtime states, alarms/events, UI viewport/selection, and communication sessions are transient. Experiment reports are persisted separately. Startup opens the most recently saved definition, stopped at initial conditions. A fresh installation opens the Packaging Line; upgrades seed any missing built-in example without overwriting saved projects. Explicit Save includes current command/fault configuration. Reset restores the definition captured when the project was loaded/edited; saving does not redefine the current runtime's reset baseline until reload. `migrateProject` accepts schema v1 and rejects unknown versions; no older schema exists to migrate yet.

## Communication and security

WebSocket clients receive a complete consistent snapshot on connection, followed by changed equipment states and new events at 5 Hz. Physics runs separately from transport frequency. Slow consumers above 1 MB queued data are disconnected and must reconnect for a fresh snapshot. Browser refresh/closure does not control server lifecycle.

OPC UA runs inside the same backend process, independent of browser sessions. Namespace and NodeIds are generated from model metadata, project ID and equipment ID. Read values carry source timestamps and quality status; writable nodes validate session role, Boolean/Double datatype, range, control mode and interlocks before submitting commands. Read-only variables are never writable. The production profile uses Basic256Sha256 SignAndEncrypt for sessions (the standard unsecured discovery endpoint is restricted to discovery services), rejects anonymous sessions and untrusted certificates, and requires an operator password. Development explicitly enables unsecured transport and anonymous reads; writes always require the configured operator. This release has one configured operator role and an anonymous read-only development role, not a user-directory/admin UI.

The web API has optional bearer-token authentication on loopback, required when binding remotely, and rejects cross-origin requests. WebSockets authenticate via a same-site cookie set by the local application when an access token is entered. Remote web deployment needs TLS termination and host/firewall controls. It is not a hardened multi-tenant service. OPC UA only exposes simulated objects; no client or bridge to real equipment exists.

## Editor and remaining product backlog

Implemented: library search, drag/drop, reusable symbols for all initial types, click/Shift-select/select all, move, delete, copy/paste/duplicate, undo/redo, horizontal alignment, grid snap, zoom/pan/bounds-based fit, port connections with server validation/removal, properties/labels/parameters, mode/commands/faults, save/open/rename/duplicate/delete/import/export, live events/alarms and session count.

Remaining: marquee selection, context menus, custom connection waypoints/obstacle routing, configurable grid/snap, per-category collapse, vertical/distributed alignment, rotation, persistent UI layout, graphical controller authoring, multi-step scenario sequencing, per-session diagnostics, full user/role management, collaborative edit conflict detection, material branching/merging, production recipes, formal line balancing and more advanced hydraulic models. Controller definitions can currently be authored through validated imported JSON. Graphical fault-window schedules, saved experiment comparisons, a searchable I/O monitor and live station performance are implemented. The UI uses a compact engineering-workbench layout with plain section labels, docked panels, grid-aligned property fields, inline production readouts and tabular event/data rows. Large promotional headings, KPI cards, decorative empty-state artwork and rounded callouts are removed. Library categories collapse, Ctrl/Cmd K focuses search, running configuration fields are disabled, and the fault panel shows applicable fault types. UI chrome and the reusable SVG symbol styling are maintained separately. SVG artwork uses orthographic industrial elevations, neutral steel surfaces, consistent fine outlines, bolted frames, cabinet doors and instrument details. Cast shadows, bright enamel gradients, decorative checkmarks and isometric package blocks are removed. Small square-corner nameplates, explicit status labels and backend-owned moving cartons preserve clarity; changing appearance never advances physics. Equipment and product artwork defaults to a 1.35× display scale with matching connection anchors. The canvas toolbar’s Symbols slider adjusts that scale from 80–160% in 5% steps, during editing or live execution. The preference is validated and stored locally in the browser; size changes refit the viewport and update connection anchors without saving or resetting the project. The SVG viewport follows the actual canvas dimensions and fits the full drawing on resize, including the extra width reclaimed when the palette hides during running. Pause/Stop restores the palette. Full-screen live view uses the browser Fullscreen API when available, with an expanded in-window fallback. It hides both sidebars, diagnostics, the title/footer and editor tabs/actions; runtime controls, production metrics, zoom/fit and symbol sizing remain available. Exit or Escape restores the previous workspace and panels, including when fullscreen is exited through browser controls. It is session-only and does not issue simulation commands or project edits; scene dragging/wiring and editor shortcuts are disabled in this view. These display changes leave project coordinates and equipment identities unchanged.

## Verification boundaries

Unit/integration checks exercise process physics, deterministic repeatability, command ownership, fault models, validation, SQLite, and independent node-opcua clients. Playwright exercises the compiled application, editing/persistence and headless continuation. These are local acceptance tests; Docker packaging is supplied but should be built and validated on the target host. Kepware/ThingsBoard integration and third-party client interoperability beyond the independent node-opcua client have not been certified.
